# 신청 조건·준비 기록 암호화

Spring의 `jibro_notebooks.payload`를 AES-256-GCM으로 암호화합니다. 생년월일·주택 보유·가구원·소득·자산·공고별 체크와 알림 읽음 기록이 포함됩니다. 저장마다 96비트 난수 IV, 128비트 인증 태그를 쓰고 형식 버전·키 ID·회원 ID를 추가 인증 데이터로 묶습니다. 다른 회원의 암호문을 복사하면 복호화가 실패합니다.

## 키 보관

운영은 서버 비밀 변수 `JIBRO_NOTEBOOK_KEYS`가 필수입니다. 형식은 `{"active":"키ID","keys":{"키ID":"32바이트 난수의 base64url"}}`입니다. 실제 키를 명령줄 인수·로그·Git·브라우저에 넣지 않습니다. 키가 없거나 잘못되면 서버가 시작되지 않으며 평문 저장으로 우회하지 않습니다.

local 프로필에서만 첫 실행에 `backend/.local-data/notebook-keys.json`을 생성합니다. DB 파일과 함께 종료 후에도 남습니다. 기존 기록이 있는데 키 파일이 없어지면 새 키를 생성하지 않고 시작에 실패합니다. 원래 키를 복원해야 합니다. POSIX에서는 키 파일 권한 0600을 쓰고 Windows에서는 상위 폴더 ACL을 상속하므로 해당 폴더의 접근자를 제한하세요. 운영에 로컬 테스트 키를 사용하지 않습니다.

키를 잃으면 DB만으로 준비 기록을 복구할 수 없습니다. DB 백업과 별도로 접근 제한한 키 백업을 보관하고 복구를 검증합니다. 이전 Site 키는 새 키로 대체해서 가져올 수 없습니다. 실제 이관 시 [원본 키와 DB를 함께 사용하는 절차](SPRING_MIGRATION.md)가 필요합니다.

## 키 교체

`keys`에 새 키를 추가하고 `active`만 새 ID로 바꿉니다. 기존 키를 남겨둔 채 배포합니다. 회원 기록을 읽을 때 이전 키 암호문을 새 키로 다시 암호화합니다. 내용·revision·수정 시각은 바꾸지 않고 기존 payload/revision 비교와 회원 잠금으로 사용자 저장을 덮어쓰지 않습니다.

아직 읽지 않은 기록과 과거 백업에는 이전 키가 필요합니다. 모든 행과 복구 대상 백업의 전환을 확인하기 전에 이전 키를 지우지 않습니다. Spring은 평문 payload를 자동 수용하지 않습니다. 옛 평문 기록이 남아 있다면 별도 통제된 사전 변환이 필요하며 이관 도구는 이를 실패로 보고합니다.

## 보호 범위

서버에서 표시할 때 복호화하므로 종단 간 암호화는 아닙니다. 비밀번호는 scrypt 단방향 해시이며 세션·메일 토큰은 SHA-256 해시로 저장합니다. 이메일·닉네임·동의 시각 등 회원 테이블 필드는 이 AES 암호화 범위에 포함되지 않습니다. 운영 DB·백업 암호화와 접근 제어는 호스팅에서 별도로 설정해야 하며 특정 공급자의 암호화를 자동으로 보장하지 않습니다.

테스트는 합성 이전 Worker 암호문과 새 Spring의 호환, 다른 회원 접근 차단, 변조/키 누락 거부, 키 교체와 동시 수정 보호를 확인합니다. 실제 운영 키나 회원 정보는 테스트에 사용하지 않습니다.
