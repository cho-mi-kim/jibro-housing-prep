# 신청 조건과 준비 기록 암호화

`jibro_member_notebooks.payload` 전체를 서버에서 AES-256-GCM으로 암호화한다. 생년월일, 주택 보유 여부, 가구원 수, 소득·자산, 준비 기록, 공고별 확인 기록이 포함된다. 저장마다 무작위 96비트 IV를 생성하고 128비트 인증 태그를 사용한다. 형식 버전·키 ID·회원 ID를 추가 인증 데이터에 묶으므로 다른 회원의 암호문을 복사해도 복호화되지 않는다.

## 키 설정

서버 전용 비밀 환경변수 `JIBRO_NOTEBOOK_KEYS`가 필수다. 형식은 `{"active":"키ID","keys":{"키ID":"32바이트 난수의 base64url 인코딩"}}`이다. 인증용 `JIBRO_AUTH_SECRET`과 별개의 암호학적 난수를 사용한다. 실제 값은 소스, 프론트엔드 환경변수, 로그, 명령줄 인수, 저장소에 넣지 않는다. 운영 환경과 미리보기 환경의 키도 공유하지 않는다. Sites 비밀 환경변수로 설정하고 새 환경 리비전으로 배포한다.

키가 없거나 잘못되면 기록 읽기·쓰기를 실패 처리한다. 평문 저장이나 다른 키로의 임의 대체는 하지 않는다. 신청 조건을 포함한 가입은 키 설정을 가입 처리 전에 확인한다. 로컬 미리보기는 임시 DB와 함께 폐기되는 일회용 키를 사용한다. 운영에서 로컬 키 자동 생성 코드를 사용하면 안 된다.

키를 잃으면 암호화된 기록을 복구할 수 없다. 운영 키와 이전 키는 담당자의 접근을 제한한 비밀 관리 도구에 별도로 보관하고, 교체 전에 복구 절차를 준비해야 한다. Sites가 비밀 값을 다시 보여주지 않는다는 점을 고려한다. DB만 다른 환경으로 복사해서는 안 되고 해당 키도 안전하게 이관해야 한다.

## 기존 기록과 키 교체

로그인된 사용자가 계정 정보를 불러오면 서버가 기존 JSON 기록을 최대 25개씩 암호화한다. 회원 본인의 기록을 읽을 때에도 이전 평문이나 이전 키의 암호문을 현재 키로 바꾼다. 변경 시 이전 payload와 revision이 모두 같을 때만 갱신한다. 사용자의 내용, 수정 시각, 기록 버전은 그대로 두며 동시 저장을 덮어쓰지 않는다. 변환 실패 시 기존 데이터는 남기고 민감한 값 없이 오류 종류만 기록한다.

배포 후 DB 뷰어에서 `payload`가 `jibro:encrypted:v1:`으로 시작하는지 모든 행을 확인한다. 25개가 넘는 기존 행은 로그인 상태의 계정 조회를 반복해 처리하고, 남은 평문이나 실패 행이 없는지 재확인한다. 현재 행이 바뀌어도 과거 DB 복구 지점·백업의 평문까지 지워지는 것은 아니다. 백업 접근 및 보존 정책을 별도로 관리해야 한다.

키 교체는 `keys`에 새 키를 **추가**하고 `active`만 새 ID로 바꾼다. 이전 키로 암호화된 모든 행과 복원에 필요한 백업이 없어졌다는 것을 확인하기 전에는 이전 키를 제거하지 않는다. 읽지 않은 기존 회원 기록은 이전 키를 계속 필요로 한다. 삭제된 키를 복원할 수 없다면 해당 기록도 복원할 수 없다.

## 보호 범위

이는 저장된 준비 기록에 대한 애플리케이션 암호화다. 화면에 보여주기 위해 인증된 요청에서 서버가 복호화하며, 종단 간 암호화는 아니다. HTTPS 전송, HttpOnly/Secure/SameSite 세션, 회원 ID 접근 제한, CSRF 검증, 요청 제한은 그대로 유지한다. 로그인 비밀번호는 기존 scrypt 단방향 해시를 유지한다.

인증 라이브러리가 사용하는 이메일·닉네임·세션 메타데이터는 인증 테이블에 그대로 저장되고 D1의 저장 장치 암호화로 보호된다. 이 필드들이 위의 추가 암호화에 포함된다고 설명하면 안 된다. `admin` 테스트 로그인 설정은 변경하지 않으며, 테스트 회원의 준비 기록에도 동일한 암호화가 적용된다.

`npm run test:account`는 암호문 확인, 계정 간 격리, 변조 거부, 키 누락, 키 교체, 기존 기록 변환, 동시 편집 보호와 인증 흐름을 검사한다.
